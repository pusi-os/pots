# Pots Build

**Last verified:** 2026-11-21

Pots Build is an **Android-only** coding environment inside the Pots app. It is a separate *surface* from chat — no shared conversation store, no sandbox tools — but it is not necessarily a separate *Linux*: when the chat sandbox also runs Debian, both work in the same install. What it does share with chat is the provider: the agents it runs are pointed at whatever provider, model, key and endpoint Settings is on, so there is no second account to log into.

It is a **single screen with three states** — set up Linux, pick a project, work in that project's terminal.

## Concepts

### Separate product surface

Pots Build is opened from the sandbox using the action after **Packages**, shown on Android. The action is also available before the sandbox is installed. Once Linux is installed it can also be opened from the Linux Sandbox settings card. It takes over the whole screen: no navigation destination, no second launcher icon, and no place in the back stack. A close button in its top bar and the system back gesture return to the screen it was opened from, leaving any drafted message intact. Inside a project, the same top-bar button and system back step back to the project list instead. The mode is not persisted across app restarts; it survives rotation only.

### Which Linux it runs in

Pots Build is always Debian: its coding agents are vendor scripts that expect glibc and apt.

Debian has exactly one install on the device, normally under app-private `pots-build/`. Pots Build works in it unconditionally, and never moves. What varies is whether the chat [Linux sandbox](sandbox.md) is pointed at the same install:

- **Shell integration is Debian** (the default) — both use the *same* install. Whichever surface installs it first, the other finds it already there: set Linux up in Settings and Pots Build opens straight on the project list; install from Pots Build's setup screen and the sandbox reports itself ready. Uninstalling from either removes it for both, and both dialogs say so.
- **Shell integration is Alpine** — that runs in a separate Alpine under app-private `linux-sandbox/`, and the two coexist.

The chat sandbox can be switched between the two at any time from Settings, and neither install is touched when it happens — so a Pots Build project terminal is never disturbed by that choice. The sandbox can also copy a home directory across when switching, but never the coding agents: their binaries are built for one distribution's libc, and Pots Build installs them per environment. (A Debian installed by an earlier build that put it under `linux-sandbox/` is found and used where it is, rather than downloaded again.)

Either way `/root` (agent binaries and config) is on the rootfs, and an external-files folder is bind-mounted only to `/root/projects`, so project code stays USB/MTP reachable without putting executables on storage that Android often mounts noexec. That projects folder is the same one in every arrangement, so projects are unaffected by the sandbox's distribution.

### Set up Linux

First run shows a single setup card: a beta notice, a short explanation, a checkbox per coding agent, and one **Install Debian** button. The setup title and description mark the feature as beta. Install downloads a Debian Bookworm rootfs from the Linux Containers image index (architecture-matched: arm64, armhf, amd64, i386), extracts it, configures DNS, then runs `apt-get update` and installs the essentials every project needs — bash, ca-certificates, curl, wget, git, nano, less, unzip, python3, tar, coreutils and libatomic1. The last one is not for a project but for the agents: the Node runtime their installers unpack from nodejs.org links against `libatomic.so.1`, and a bookworm rootfs ships only `libgcc_s.so.1`, so without it `node --version` dies with `error while loading shared libraries` and exit 127 before a line of JavaScript runs. Nothing else in the list pulls it in — Debian's own `nodejs` and `python3` depend on `libnode108`/`libgcc-s1`, neither of which is that library. Any agents ticked beforehand are installed straight after, so a fresh system arrives ready to use. If a Debian is already installed — because the chat sandbox put one there — this step is skipped entirely and only the ticked agents are installed.

Progress replaces the install button (download percent, extract, configure, base packages, per-agent), with Cancel next to it. Cancelling or failing deletes the partial rootfs so the retry starts clean; a failure message stays on screen. A Debian install is only considered complete once its base packages are in, so an interrupted install can never present itself as ready.

### Install log

Every agent install streams its own console output into a small monospace pane under the progress bar, the way a terminal would show it, and the pane stays on screen after the install ends — including when it failed. It is drawn on both surfaces an install can end on: the setup screen while the install runs, and the project list, which is where a failure lands when Debian was already installed and the screen has switched back. That is deliberate: an install that stops is reported as *Could not install Hermes*, which names no cause, so the log next to it is the only place the reason exists. It used to exist nowhere at all: the whole output was collected into one string and one line of it went to logcat, where a phone's 256 KB buffer had already been overwritten by system noise by the time anyone looked.

The pane keeps the last 64 KB, cut to whole lines, with `\r` ending a line as well as `\n` — git redraws "Receiving objects" in place and uv redraws its spinner, so splitting on newlines alone would collapse a download into one unreadable string. ANSI colour and cursor sequences are stripped (installers emit them for the terminal they think is watching), and the view follows the tail until the reader scrolls up, so a running install does not yank the text out from under them. It republishes at most every 200 ms: git writes in bursts of kilobytes and repainting per chunk is what makes a screen unusable. Text is selectable, so a failure can be copied out of the app.

An install that prints nothing for twenty minutes is treated as hung and killed, because the installer's own `curl` calls have no timeout and a stalled TLS handshake would otherwise wait out the whole hour. It is a long silence on purpose — `npm install` in a pipe prints nothing until it is done, and a shorter window would kill a working Pi install. The log is not cleared on failure — it is the explanation.

LXC images ship `etc/resolv.conf` as a symlink into systemd-resolved under `/run`, which does not exist under proot. Install replaces that link with a plain file pointing at public DNS (`8.8.8.8` / `8.8.4.4`) so apt and HTTPS work.

Debian’s package manager relies on hardlinks when unpacking packages. On Android those often fail inside the app sandbox, so Pots Build starts proot with hardlink-to-symlink emulation (and the companion lstat fix) before any apt work. Without that, the base-packages step fails with a dpkg subprocess error even though `apt-get update` succeeded.

Pots also tells apt to keep running as (proot's fake) root instead of dropping to its `_apt` user for downloads. Work profiles, Dual Space, Private Space and system clones block that user switch, which otherwise makes `apt-get update` fail and every package look missing. The setting lives in the rootfs, so apt run from the Terminal or by an agent picks it up too.

### Coding agents

Three agents are offered — **OpenCode**, **Pi** and **Hermes** — and each is installed by the installer its own developers ship, because that is the only path that pins what actually gets installed. OpenCode's installer is fetched from the project's own repository (`raw.githubusercontent.com/anomalyco/opencode`, branch `v1`) rather than from `opencode.ai/install`, which answers 307 through Cloudflare from a sandbox; the script resolves the newest release itself and downloads the static binary from GitHub Releases into `~/.opencode/bin`. Pi is a Node.js program, and the Node it needs (22.19+) is newer than bookworm's, so a Node runtime is unpacked into `~/.local/share/pi-node` from nodejs.org for the running architecture first — Pi's own script refuses to fetch Node without a terminal to ask on, and an agent install has none — and then `https://pi.dev/install.sh` runs, which resolves one pinned release from its lock file into `~/.pi/agent` and links `~/.local/bin/pi` at it; that is also the layout `pi update` maintains, and npm would instead resolve transitive ranges. Hermes is not usable from PyPI — the only release there is an old build without its web app — so it comes from its repository: `NousResearch/hermes-agent` cloned one commit deep into `~/.hermes/hermes-agent` (`git clone --depth 1 --branch main`), because the installer's pin step walks the history to prove a commit is an ancestor of the branch and a depth-1 clone has no history to walk — and because the latest Hermes is what the owner asked for, nothing is pinned. Then that checkout's own `scripts/install.sh --non-interactive --skip-browser --skip-computer-use --channel main`, which pins uv and Python, installs the dependency tree and builds the `hermes` command into `~/.hermes/hermes-agent/.hermes/bin`, linked into `~/.local/bin`. The release tags are fetched right after the install (`git fetch --filter=blob:none origin '+refs/tags/*:refs/tags/*'`, refs only, no file contents), because `hermes --version` — the version the agent row shows — names the newest release tag reachable from `HEAD`, and a depth-1 clone carries none: without that fetch the row reads `git.<sha>` where the release number belongs. Everything is written under `/root` on the rootfs (executable); only project folders live on the external bind. Proot injects every agent bin dir into `PATH` for install and detection. Login shells (every project terminal) rebuild `PATH` from system profile files and would otherwise drop those dirs, and Pi's Node runtime sits in a third directory — so Pots Build writes a small system profile snippet that keeps every agent dir on `PATH` for login shells, links found binaries into `~/.local/bin`, and starts an agent session via the resolved absolute path. An agent counts as installed only when its binary is actually reachable afterwards and answers a `--version` probe, regardless of what the installer's exit code claimed — a shim left behind without the runtime it needs is not an install; agent state is probed from the live environment rather than remembered in a file.

An install starts by asking what a previous one left behind. Every path in the agent's own install list is looked at before anything is created: a path that exists while that same `--version` probe does not answer is the debris of a run that stopped halfway — an installer writes its files before it links the binary, so the tree is there and the command is not. The cleanup runs before `mkdir -p`, because a directory made a moment earlier would look like a leftover itself, and it asks nothing, because this is part of the install rather than a removal and it only ever takes what has no binary behind it. Its lines go to the install log in the order it acts: `pots: <agent>: leftovers found (<paths>)`, then the free space — only when something is actually going to be taken — (`pots: <agent>: df -h /root | tail -1 → <the line>`, since a full disk is the likeliest reason the previous run died), then `pots: <agent>: cleaned (<paths>)`, or `pots: <agent>: nothing to clean` when there was nothing to take. A binary that answers means those paths are the installation rather than debris, so nothing is touched and the log stays quiet: a reinstall is an update, and an update must not begin by deleting what it updates. Only the paths the agent's spec names are considered — no `find`, no guessed directories, and no `git clean -fdx`, which would take `uv.toml` and the `.git/info/exclude` line Pots writes itself. Hermes' 5 GiB checkout is deliberately not one of them: it is the agent's bulk path, repaired by the installer that follows rather than deleted and downloaded again.

Every delete passes one guard, and it reads the agent's `keepPaths` — what the owner would lose if it went: each agent's own configuration and data, the Node runtime Pi and its web panel run on, and for Hermes the credentials, the state database, the profiles, the board, the cron jobs, the sessions, the memories and the state snapshots under `/root/.hermes`. A path that is a kept path, a parent of one, or inside one is refused and named in the log instead — `pots: <agent>: refusing to remove <path> — it holds user data` — rather than taken. The parent half is the load-bearing one: `/root/.hermes` holds `auth.json`, `state.db` and `profiles/`, so the directory itself can never be a delete target, while `hermes-agent` beneath it is an ordinary child the removal action may still offer. The same guard stands in front of that removal action, so a kept path is not deletable by either route; a comparison that ran only downwards would be a formality, since `keepPaths` names directories as often as files.

That same `--version` answer is the version **Pots Build** shows next to each installed agent, in its agent rows — the one place the list and its install/update/remove buttons live; the Settings → Sandbox card does not repeat them. The version is read from the first `X.Y.Z` the agent printed and cached with the rest of the environment state, so no shell runs to render the rows. An agent whose probe printed nothing usable is listed as *version not determined* rather than guessed at or called latest. Nothing upgrades an agent on its own: there is no background update, and the installed release stays until the user installs it again.

An agent row's actions are icon buttons rather than words — check the version, install, update, remove — each carrying its label as the accessibility description and localized, so a Russian UI reads Russian. Removing asks first and offers Hermes' checkout as a separate tick, since that is the one path measured in gigabytes. Under the row sits the agent's own description, collapsed by default: a couple of sentences on what the agent is and what it does in the sandbox, then GitHub and documentation buttons that open the system browser, without visible captions so the row stays one line tall.

While any of those actions runs, the row keeps its place but replaces the buttons with a progress bar and the log. Install and update get an indeterminate bar, because the wait is the network's and the registry's and there is no denominator to be honest with; a removal gets a determinate one, because the paths it deletes are known before the first delete, so the bar counts `сделано / всего` for real. The log is the same monospace pane the install surface uses, and it belongs to the agent the running job is for — one job runs at a time, so the row that owns it is the row that shows it. A removal has no installer output of its own, so it writes its own lines: one per path with what became of it — `удалено` with the bytes freed, `не было` when there was nothing there, `не удалось` with the cause when the path survived — and a summary that counts only the paths and bytes that actually went. That is the difference between a delete that failed quietly and one the owner can see: Hermes' 5 GiB checkout takes minutes, and the row says so instead of sitting on the old version until the buttons turn into "Install".

Hermes is the only one of the three that needs help from the sandbox itself, for reasons that have nothing to do with each other.

**uv must copy, not hardlink.** `hermes pm` installs the Python tree with uv, which normally hardlinks its cache into the venv, and the install dies at `failed to hardlink file … Operation not permitted (os error 1)`. Both paths in that message carry a `.l2s.` prefix — the mark proot's `--link2symlink` emulation leaves behind (`l2s` stands for link-to-symlink): an earlier hardlink was already turned into a symlink, and hardlinking that artifact on is what the guest refuses. So this is not a missing proot flag and not a cache that went bad; uv has to copy. Neither the environment nor a config file can tell it so at the stage that fails. `pm` filters the environment it hands its uv children (`pm/environment.py`, `_base_environment`, keeps index settings only), points `XDG_CONFIG_HOME` at a temporary directory, and builds its own runtime (`/root/.hermes/installs/<id>/pm-runtime`) through `PythonEnvironment(…, no_config=True)`, i.e. `uv --no-config` (`pm/runtime_stage.py`). Pots still writes a project-level `uv.toml` (`link-mode = "copy"`, `no-cache = true`) and exports `UV_LINK_MODE`/`UV_NO_CACHE`, because they cost nothing and cover the stages uv runs inside the checkout — but the runtime stage ignores all three.

What does reach that stage is the command line, and Pots changes it at the only place it can: `pm` never calls `uv` by name from `PATH`, it executes the absolute path of its own store entry (`/root/.hermes/tools/uv-<version>-<target>/uv`). Pots moves that binary to `uv.real` and puts a small `sh` wrapper in its place, so every `pm` call — now and on later `hermes update` runs — goes through it. Two details of that wrapper matter. `--link-mode` is not a global uv flag (`uv --link-mode=copy cache prune` answers `unexpected argument`), so the flags cannot be prepended; the wrapper inserts them after the subcommand, and only for `venv`, `sync` and `pip install|sync`, which are the calls that link files and accept the flag — only `cache prune`, `cache clean`, `python find` and `pip check` reject it, and `pm` makes all of those calls, while `lock` and `export` do accept it (which is why the wrapper is an allowlist rather than a deny-list). And a wrapped binary would not survive on its own: every explicit `hermes pm install` re-hashes the tool closure and publishes a pristine uv over the entry when the digest no longer matches — quietly undoing the wrapper a moment before the stage it was meant to fix. The wrapper step therefore rewrites that one recorded digest, using `pm`'s own `pm.store.tree_digest`, so the entry still verifies and the wrapped binary stays. That rewrite goes through `pm.filesystem.durable_write_bytes` and reads as `utf-8-sig`, the same pair of calls `pm` makes on `facts.json`: a plain rewrite would truncate first and leave a half file behind if the install were killed there, which is the kind of breakage this whole path exists to remove.

The first install on a fresh device needs one more step, because uv does not exist until the installer downloads it — after the wrapper step has looked — and `pm` then installs its own copy. The command retries the installer once, wrapping again in between; the clone, uv and Python are already on disk, so the retry is the short path. Before any of this runs, a one-time marker removes the half-built runtime and the uv cache left by earlier failed attempts (`rm -rf /root/.hermes/installs/*/pm-runtime /root/.hermes/cache/uv`) — but only when a scan of those directories actually finds a `.l2s.` artifact, or cannot run at all; a scan that cannot run must not be read as clean. A working install therefore keeps its runtime instead of rebuilding it for nothing, and a device with nothing built is left for the next run to judge: the marker is set once the question has been answered, except in that last case.

The install log carries a hardlink probe so the next failure explains itself rather than being guessed at: it prints the device ids of the two directories uv links between, attempts the link *between* them, counts the `.l2s.` artifacts in the built runtime, and shows where uv actually lives and how `pm` calls it. A probe that linked two names inside one directory — as an earlier version of this did — reports success even where the real link is refused, which is why it is worth nothing here. The device ids are the one fact that settles the question: different filesystems mean copying is the only option, whatever the flags say.

**The stable channel hangs the install.** The installer's default channel resolves the latest release tag and fetches it into the clone, and `git fetch` of a tag into a `--depth 1` clone has to download the tag's whole history — 643k objects, over 250 MB, more than 45 minutes on a phone — after which `merge-base --is-ancestor` cannot answer in a shallow clone and the checkout is kept as it was anyway. Pots installs with `--channel main`, which follows the branch and skips the fetch entirely. The trade-off is deliberate: future `hermes update` runs follow `main` rather than releases.

**The pin is the fallback's address, not the install's.** `hermes-webapp.pin` names the hermes-agent commit CI builds the panel bundle from, and it is used in exactly one place: when every on-device renderer build failed, the checkout is moved to that commit (`git fetch --depth 1 origin <pin>`, `git checkout --force --detach <pin>`) and the bundle CI built from it is unpacked and served. The install itself never pins: it follows `main`, because the installer's own `--commit` path first proves the commit is an ancestor of the branch, and that walk needs a history a depth-1 clone does not have — the pinned install used to die on the phone with `commit … is not on branch main`, before `hermes` was ever built or linked into `PATH`. Keeping the checkout on a release also left the sandbox a version behind the renderer it could build for itself. So a build that ships no bundle pins nothing at all, and a build that ships one keeps the pin only as the address of the last resort.

**A checkout without a working tree is repaired, never trusted.** `git clone` creates `.git` first and the files last, and the fallback's `checkout --force --detach` can be killed the same way, so a run interrupted by a dying proot, a dropped network or a full disk leaves a `.git` with no tree — and `rev-parse HEAD` answers there, which is exactly why a check built on it alone passes. The next run used to see `.git`, skip the clone and die on a `scripts/install.sh` that was not there (`bash: … No such file or directory`, exit 127), twice: the retry repeated the same path. So the checkout is now validated on two facts before anything else touches it — HEAD resolves, and `scripts/install.sh` is in the tree — and a broken one goes through a ladder that is judged by those two facts and never by an exit code (`git reset --hard` answers 0 on a HEAD that does not resolve, and a step whose output is piped to `head` answers with head's status): `checkout --force --detach HEAD` puts back what HEAD has and the tree does not, and only when that cannot help — a clone that never finished, a repository with no commits — the 5 GiB checkout is deleted and cloned again with the flags the first clone used. `git clean -fdx` is deliberately not in the ladder: `uv.toml` and the `.git/info/exclude` line are Pots' own files, and a re-clone starts without them, so the ladder rewrites both. The log carries the state and the cause — `pots: hermes checkout: broken (<reason>)`, then the `df -h /root` line and `git status --short` before the repair, then `repaired at HEAD` or `re-cloned`. A repair that cannot finish names free space or the network and stops the install there, with that line last in the log, instead of dying inside `install.sh`; and the installer's retry, which re-validates the checkout at its top, does not try the download a second time once the ladder has given up.

**The renderer is built on the device, in a proot call of its own.** `hermes webapp --build-only` is a `pnpm install` of the renderer's own workspace (`.build/webapp-workspace`, at the root of the Hermes checkout — `apps/desktop/scripts/build-webapp.mjs` mirrors the inputs there and writes the finished bundle to `apps/desktop/dist-webapp`) followed by vite. It cannot share the proot call the agent install runs in: pnpm 12 stages every imported package in a `…_pacquet-stage_…` directory inside the package and renames it into place, and under `--link2symlink` — the flag apt needs for the base packages — that rename answers `No such file or directory (os error 2)`, so the build aborts with `failed to place imported file …` and vite never starts. Without the emulation the same tree builds a complete 45 MB bundle (1058 files under `assets/`, `index.html` referencing `./assets/index-<hash>.js`) in a little over seven minutes — pnpm install 1m 56s, vite 4m 3s — where with the emulation the same build dies within 24 seconds (`rc=1`); measured on a Debian 12 arm64 rootfs from the same LXC index, with the Node and pnpm `pm` itself installs (26.12.1 / 12.15.0). So the build is a second proot invocation with `-L` alone (`-L` is the separate `fix_symlink_size` extension, not part of the emulation), run right after the agent is installed and on PATH. That chain as a whole is bounded by one budget of thirty-five minutes, not by the installer's own timeout, which covers the installer alone: an attempt is started only while at least ten minutes remain — the measured seven-minute build plus a margin, not the attempt's own twenty-five-minute hang deadline, which would end the chain after two attempts — and a running attempt is cancelled when the budget ends: the cancellation reaches the wait loop of the build's own proot call, which kills the process before the fallback unpacks anything (a chain can overrun the budget only by the blocking clean of the attempt it was in, five minutes at most, never by a whole attempt). A chain that runs out serves the shipped bundle instead of waiting longer, logging `renderer: device build budget spent, serving the shipped bundle`. Every attempt starts with a line carrying what is left of the budget (`renderer: building on device (attempt 2 of 3, link2symlink, copy import), ~24 min left of the build budget — about seven minutes`), so the wait counts down on screen instead of reading as a stall. Thirty-five minutes pays for three measured builds with room for a slow network, and is well under the seventy-five a chain of three full attempt timeouts would cost. Three attempts are made, each from a wiped pnpm store: without the emulation and with `pnpm_config_package_import_method=copy` in the proot environment; then *with* `--link2symlink` and the same setting — the installer wrote the checkout, the venv and the `pm` tools under the emulation, so this is the only attempt that runs in that tree as the install left it, and the only place the device itself can answer whether those `.l2s.` artifacts are what break the build; then without the emulation and without the setting, which says whether `copy` was needed at all. The store has to be wiped rather than moved — Hermes forces pnpm's store to `$HERMES_ROOT/cache/pnpm/{store,cache,state}` itself (`pm/packages.py`), and a store a failed attempt leaves behind is made of `.l2s.` symlinks, which a later build dies against in rolldown with `Could not resolve '../cjs/…'`. The environment is also the only channel that reaches pnpm 12: pacquet reads `pnpm_config_*` and ignores `npm_config_*`, so a `$HERMES_HOME/npmrc` hook cannot carry these settings at all (its `npmrc` is for auth, registry and TLS), and settings alone never fix the failure anyway — the staged rename is independent of `package-import-method`, which is why dropping the emulation is the whole fix. When every attempt fails, the panel falls back to the bundle CI built: the checkout is moved to the commit `hermes-webapp.pin` names (`git fetch --depth 1 origin <pin>` then `checkout --force --detach`), its release tags are fetched again so the version is a release rather than a SHA, and the archive is unpacked into `~/.hermes/webapp-dist` and served through `HERMES_WEBAPP_DIST`. That whole path is one line in the log before it starts — `renderer: build failed, falling back to the shipped bundle at <pin>` — and a checkout that could not be moved stops it there with the cause as the last line, because the panel refuses a renderer built from another commit. The install log names the path that won (`renderer: built on device (attempt 1, no link2symlink)`, `… (attempt 2, link2symlink, copy import)`, `… (attempt 3, no link2symlink, no import method)`, or `renderer: shipped bundle`), a build answered `is up to date` is logged as `renderer: attempt N built nothing — Hermes answered 'up to date', so --force-build did not reach it` rather than counted as a success, and that variable is set for the shipped bundle only — naming it after a device build would tell Hermes the renderer is ready and stop it from ever rebuilding.

**What the panel serves is decided by what it was built from.** A build that wins stamps its commit in `~/.hermes/webapp-dist/.pots-built-from` (atomically, after the page and its `assets/` are there), and a build that fails leaves no stamp, so a half-written bundle can never be read as this checkout's own. At start the panel reads three facts — the commit the checkout is on, the commit the stamp names, and the commit the shipped bundle's pin names — and serves a renderer only against the Hermes it was built from: a device build whose stamp is the current `HEAD` (which is the ordinary case now that the install follows `main`), or CI's bundle while the checkout is its pin. Both can be on disk — an earlier install fell back, a later one built — and then the device build wins, because that one *is* the sandbox's Hermes. Anything else is a sentence on the row naming the two commits and pointing at reinstall, never a page that opens blank.

Both agents' installers are also run with stdin closed (`< /dev/null`), and the sandbox starts proot with `--kill-on-exit` on every call — not just for installs. That flag is why killing the app during an install does not leave `git` and `uv` running over half a written pack file, and it applies to project terminals too: a background process started in a shell dies with the session's proot, which is the behaviour the guest tree kill was introduced for in the first place.

### Provider propagation

Every agent comes up on the provider Pots itself is using, with no per-agent setup: the active service instance's **provider, model, API key and endpoint** are written into each agent's own configuration file, and rewritten every time an agent session starts (and once more when an agent is installed). Switching provider or model in Settings is therefore all it takes for the sandbox agents to follow — there is no second account to log into and no endpoint to retype.

The mapping is per agent, because each reads its own file: OpenCode takes `~/.config/opencode/opencode.json` — an OpenAI-compatible `provider` entry (`npm`, `name`, `options.baseURL`, `options.apiKey`) plus the top-level `model` it starts on — and names the key variable (`{env:...}`) instead of holding the key, with the value put into that agent's own process environment, so the same file is what `opencode serve` reads; Pi takes `~/.pi/agent/models.json` (the provider as a custom OpenAI-compatible provider, with the active model in its list) plus `~/.pi/agent/settings.json` (that provider and model as the startup default); Hermes takes `~/.hermes/config.yaml` (a `providers:` entry plus the `model:` block that selects it) and keeps the key itself out of the YAML in `~/.hermes/.env`, which Hermes loads as dotenv and which is made owner-readable only. Provider and model ids are single-quoted YAML scalars so a quote in an id can never end the value early. A keyless provider — a local Ollama, which needs no key — gets a fixed placeholder instead of an empty value, because Pi rejects the whole `models.json` over a blank key and would lose the provider, the model and the endpoint with it; the same placeholder goes into Hermes' `.env` and into OpenCode's environment. Every `$` in a key is escaped (`$$`) and a key that begins with `!` gets Pi's `$!` prefix, because Pi interpolates `$` anywhere in the value — an unset name drops the provider entirely and a set one (`$HOME`) silently substitutes the sandbox's own variable — and reads a leading `!` as a command to run.

Nothing is written when Pots has no provider to give: no configured service, no model chosen yet, or the on-device model — which has no endpoint a sandbox agent could call. A half-written config would only leave an agent pointed at nothing.

Agents can be added after setup from the Debian system card on the project list, which shows the install progress on the setup surface and returns to the projects when it finishes.

### Projects

Every project is a folder under the Linux home's `projects` directory (`/root/projects` inside Debian). The project list is that folder listing, so anything created in the shell shows up. A plus button in the top bar opens a small dialog for the name; creating the folder drops the user straight into its terminal — no other steps. Names are sanitized to a safe folder name. A project with shells still open says how many, because the list is the only place to find them from; opening it goes back to those rather than starting another.

Each row carries an overflow menu with the two things that can be done to the folder itself — **rename** and **delete**. They sit behind the menu rather than on the row so that tapping a project stays what it looks like: opening it.

Renaming offers the current name and refuses one that is empty, contains a path separator, or belongs to another project — caught in the dialog, since the list of names is right there, rather than reported afterwards as a rename that quietly did nothing. Deleting asks first, names the project in the question, and says how many shells are open in it when there are any.

Both close the project's sessions, because both move the ground out from under them: the shells are rooted in that folder, and one whose working directory has been renamed or unlinked is no longer a session anybody can use. Deleting removes the folder and everything in it, following no symlinks on the way — an agent's project can hold a link into the rootfs, and a delete that followed one would take the Debian install with it. Projects created outside the app keep whatever name the shell gave them: the list addresses a folder by the name it shows rather than by a sanitized guess at it.

Above the list, an optional **Open with** row picks what a *fresh* project opens with: a plain shell (the default) or one of the installed agents. The choice is a preference rather than a per-visit pick — it is remembered until it is changed, including across app restarts, so somebody who works in Pi finds Pi selected the next morning. It has no say over a project that still has shells open — that one is resumed as it was left, and the row's choice applies to the next session started from the plus button. A remembered agent that the environment no longer has (Linux was removed and put back without it) falls back to a plain shell rather than opening a session on a missing binary.

A **Debian system** card below the list is the home for everything about the Linux install rather than the projects: which Debian it is and for which architecture, how many packages are in it, how much space the system and the project folders take, how much room is left on the device, chips to install the remaining agents, and the uninstall action. The facts are read straight off the rootfs, so the card is current every time the list is shown.

Opening Pots Build answers "is Linux installed?" from a marker file and shows the project list straight away. Everything that costs real work — probing each agent by running it, and measuring how much disk the system and projects take — happens right after and fills the card in a moment later, so an installed system never shows the setup screen while it is being checked.

### Terminal sessions

A project can have **several shells open at once** — one running an agent, another for git — switched from a tab strip that replaces the title bar at the top of the terminal. Each tab is an independent session: its own PTY, its own screen contents, its own geometry, and its own draft input line. The plus button next to the tabs starts another session, either a plain shell or an installed agent.

Tabs are labelled by what they run (an agent's product name, or "Shell"), numbered while more than one is open. The selected tab carries a close button. Closing a session ends its shell and everything running inside it; closing the last one steps back to the project list, as does the back button.

**Stepping out of a project leaves its shells running.** A build, a test run or an agent mid-task keeps going while the user reads something else or works in another project, and coming back finds the tabs exactly as they were — same scrollback, same tab in front. Closing a session is the user's decision, made from its tab; nothing else ends one. The exception is the backstop: a project nobody has reopened for an hour has its shells closed, because each one is a proot process with a PTY and a shell behind it and a project left overnight is not one anybody is still waiting on. Reopening the project at any point during that hour calls it off.

A background session still reads and parses everything its program writes, but it does not repaint the app while nobody is looking at it — its screen is brought up to date the moment its project is opened again.

An **agent session** runs that agent's CLI first and drops to an ordinary shell in the project folder when the agent exits, so a finished session is still usable rather than dead.

### Project files

Next to the session tabs — pinned, so it is always there — sits **Files**: the same file browser the chat sandbox uses, pointed at Pots Build's Debian instead. It opens on the project's own folder, and navigates the same way it does in chat: the breadcrumbs run all the way up to the filesystem root, so an agent's config under the home folder, `/etc`, or anything else in Debian is a crumb away rather than shell-only. Where it starts is the only difference between the two.

It does everything it does in chat: open a file in the built-in editor and save it back — including the extension-less and unfamiliar-extension files a project is full of, since what counts as text is decided from the bytes rather than the name — hand a file to another app on the device, import a file from device storage into the directory on screen, rename, delete, and re-list itself silently whenever the tab becomes visible, so files an agent just wrote show up without a manual refresh. Files are read and written directly rather than through a shell, so none of it depends on a session running.

Switching to Files leaves every session running — coming back finds the terminal exactly as it was, and Files finds the directory it was left in, wherever in Debian that was. The system back gesture steps Files → terminal → project list.

### Terminal

A session shows a **cell-grid terminal** sized to the visible viewport: cursor, basic colors, and common ANSI/VT control sequences, backed by an interactive login shell (`bash -l`) in the project folder. When the panel is laid out or the window changes (rotation, IME, split), Pots recomputes columns×rows from the monospace cell size, resizes the buffer, and tells the live PTY the new geometry (`TIOCSWINSZ` + `SIGWINCH`) so fullscreen apps reflow like a desktop terminal. Cell size is taken from measured text rather than from the font settings, so the row count never buys a row that only half fits and the column count never gives away a column that does. There is no app-side clear button: `clear` and Ctrl-L do it from inside the shell, which keeps what is on screen and what the running program thinks is on screen the same thing.

The grid and the PTY are held to **one geometry**, because the two disagreeing is not a cosmetic problem: an agent that paints its banner once paints it at whatever width it was told, and if that is wider than the grid, every line of it wraps and stays wrapped — nothing ever repaints it. So a session is launched with the geometry measured a moment earlier rather than the one it was created with (the viewport is measured while the agent binary is still being resolved), the first measurement of a tab is reported immediately while later ones wait out the keyboard and rotation animations, and nothing inside Debian is allowed to take the size back — the session's PTY is checked against the size the app asked for and corrected within a tick if a login script or an app moved it. A new session still inherits the last measured geometry, so it starts at the right size instead of a default 80×24.

The grid is given as much of the screen as possible: the tab strip is the only chrome above it, and the panel runs edge to edge sideways — the grid keeps a small inset of its own, so a second margin around it would only cost columns.

The session uses a **pseudo-terminal (PTY)** inside Debian (via Python’s `pty` module) so tools that open `/dev/tty` (agent CLIs, fullscreen TUIs) can start. Output is parsed by a minimal VT emulator into a character grid and rendered in Compose.

### Terminal input

The terminal has **two input modes**, switched from a key in the key row. Keyboard mode is the default.

In **keyboard mode** the grid itself is the input surface: tapping it raises the soft keyboard, and every character reaches the shell the instant it is pressed. A tab raises the keyboard by itself the first time it is shown, since a session is started to be typed at; switching back to it later does not, because that is usually to read what an agent wrote rather than to answer it. That is what lets a TUI respond while the user is still typing — typing `/` in an agent CLI pops up its command list, and as-you-type filtering works the way it does on a desktop. There is no text field and nothing to submit. While the soft keyboard is open in this mode the input bar (hint, show-keyboard) is hidden so the cell grid keeps that row; dismiss the keyboard and the bar returns. The key row stays visible either way.

In **line mode** a text field returns, and the typed line is sent in one go when the user submits. It exists because keyboard mode gives up autocorrect, swipe typing and word prediction — a fair trade for driving a TUI, a bad one for composing a paragraph-long prompt to a coding agent. The mode is shared by the open tabs and is not remembered across app runs; the half-typed line is per tab, so switching away and back does not lose it. Line mode always keeps the input bar, because that is where the draft is typed.

The switch lives in the key row rather than the input bar precisely because the bar is gone at the moment it is wanted most — mid-sentence, keyboard up, realising the thought needs composing rather than typing straight at the shell. Switching to line mode while the keyboard is open hands the caret to the text field, so typing simply carries on there.

Both modes share a **key row** above the input bar for keys a phone keyboard does not have: Ctrl, Alt, Shift, Esc, Tab, the four arrows, and Enter. The three modifiers **latch for exactly one press** — tap Ctrl, then C, to interrupt — because there is no physical key to hold down. Tapping a latched modifier again clears it. In keyboard mode the latch also applies to the next character typed on the soft keyboard, so Ctrl and a letter behave as one chord. A modifier reported by a hardware keyboard is merged with whatever is latched.

The full set of caps is wider than a phone screen, so the row scrolls sideways and its order is a ranking: Ctrl, Esc, Tab and the four arrows come first because no soft keyboard offers them at all, and Alt and Shift trail behind them. Enter and the input-mode key sit outside that scroll, pinned to the right edge, so the key that ends every command and the one that changes how typing works are always in reach. The mode key is the one cap that still works once a session has ended — it changes the app, not the shell. Hairlines mark the groups. The arrows and Enter are drawn as icons rather than printed as terminal characters — as text they came out hairline-thin and at whatever weight the platform's font happened to have. Enter is the row's action key and reads as one: a wider, filled green cap with a bright return arrow on it. Caps dim as a set while no session is running.

Presses are encoded as the byte sequences xterm defines, which is what readline and every TUI decode: Enter as carriage return, Backspace as delete, Shift+Tab as its own sequence rather than a modified Tab, Ctrl-folded characters in the control range, and Alt as an escape prefix. Arrow keys have two encodings and the terminal tracks which one applies — apps that switch into application-cursor mode expect a different form, and sending the wrong one prints stray characters instead of moving the cursor. That mode is read back from the running app and resets when the screen is cleared.

Keyboard mode works by asking the system keyboard for a null input type, which is what makes keyboards deliver raw key presses instead of composing words. Keyboards are inconsistent about honoring that, so committed text and deletion requests are handled as a second path; a keyboard that ignores the hint still delivers whole words rather than nothing. The IME action button is treated as Enter.

An app can also ask to hear about **the mouse**, which is what makes parts of a TUI clickable on a desktop — and, once the terminal answers, on a phone. While an app is asking, a tap on the grid is a click on the character under the finger, and a vertical drag is the scroll wheel, one notch per row of cells crossed, so a list inside the TUI scrolls by dragging it. Content follows the finger, the way every other list on the device does. Sideways movement is ignored, since a TUI has nothing to scroll sideways and reading it as a drag would only make taps harder to land.

Handing taps to the app costs the shortcut that otherwise raises the keyboard by tapping the grid, so while an app is asking for mouse events the keyboard button in the input bar is the way to bring the keyboard up. Nothing changes at an ordinary shell prompt, which asks for none of this: a tap there still raises the keyboard. Whatever an app turned on is forgotten when the screen is fully reset, so a stale mode cannot outlive the program that wanted it.

The input surface that does this is deliberately kept out of the way rather than laid over the grid — anything covering the grid would hide the terminal contents from screen readers, so the grid keeps its own tap handling and stays readable in both modes. Input written to the shell is queued onto a single background thread, so a keystroke never blocks the UI on a pipe write and the bytes still arrive in the order they were typed.

### Repaint pacing

The PTY hands Pots a block of output as often as the program produces one — under heavy output that is far more often than the display refreshes. Parsing every block into the cell grid happens immediately, so nothing is ever missed, but **painting is coalesced to at most one repaint per frame**. A burst of output collapses into a single redraw instead of one redraw per block, and the last state is always painted, so the final screen a command leaves behind is never the stale one. Everything the repaint needs — snapshotting the grid, scanning it for login codes, handing it to the UI — happens off the main thread, as do geometry changes. That is what keeps the rest of the app responsive while a command floods the terminal, and what keeps raising the soft keyboard from stalling.

## Behavior

- **Android only** — the entry button is hidden on iOS, desktop, and web, and the environment itself is a no-op there.
- **Network required** — the rootfs download and every agent installer need HTTPS outbound access.
- **Disk** — expect ~150 MB for the base system, more per agent; the project list reports the real figure once Debian is installed.
- **Shared or separate** — Pots Build shares its rootfs with the chat sandbox when that sandbox is Debian, and has its own when it is Alpine. Project folders are the same either way.
- **Projects survive uninstall** — removing Linux deletes the Debian system, not the user's project folders. When the system is shared, removing it from either surface removes it for both. Deleting a project is the other way round: it takes that folder only, and leaves the system alone.
- **Files are ordinary files** — project folders live in app external storage, so the browser reads and writes them directly, and a file handed to another app opens as itself.

## Limitations

- **Minimal VT set** — cursor move, erase, SGR colors (16 + coarse 256/RGB map), scroll; login URLs are captured via the `$BROWSER` wrapper Pots installs (and OSC 8/52 / plain text when present) and shown under the grid for a couple of minutes, then cleared. Same path collapses to one link (so OAuth re-prints do not stack), at most three links, and line-wrapped URLs are rejoined before scanning; no full xterm (true dual alt-screen buffers, scrollback history).
- **Mouse reporting is clicks and wheel only** — no drag-select or hover, so an app that asks to follow the pointer while it moves is answered as if it had only asked about clicks; no right button; no modifier keys on a click. A very wide grid falls back to reports an app can still read only if it asked for the modern coordinate form, which every agent TUI does.
- **Keyboard mode gives up IME help** — no autocorrect, swipe typing or predictions while keys go straight to the terminal, which is why line mode still exists.
- **Keyboards vary** — the null-input-type hint is a convention, not a guarantee. A keyboard that ignores it delivers whole words on commit rather than single presses, so as-you-type behavior degrades to word-at-a-time on those.
- **No composing region** — dead keys and IME candidate selection are not supported in keyboard mode; text arrives when committed.
- **Key row coverage** — Ctrl/Alt/Shift, Esc, Tab, arrows, Enter. Home/End, Page Up/Down and Delete are encoded and reachable from a hardware keyboard, but have no caps in the row. Function keys are not encoded at all.
- **No bracketed paste** — a submitted line is sent as plain bytes, so an app that would otherwise treat a multi-line paste as one unit still sees it as ordinary input.
- **Full-grid redraw** — a repaint rebuilds the whole grid rather than the changed cells, so a screen that is mostly static still costs a full pass. The per-frame cap is what keeps that affordable; there is no damage tracking.
- **Resize debounce** — geometry updates are lightly debounced and applied off the main thread, so very rapid layout thrash may lag a frame behind the pixels.
- **Cancel is cooperative** — it takes effect while downloading and between install steps, not in the middle of a running `apt-get`.
- **Background** — long installs or agent sessions can be killed if Android reclaims the process (foreground service is planned). Sessions survive leaving a project but not the app being killed, and a project left alone for an hour has its shells closed for it.
- **The file browser cannot create** — it renames, deletes, edits and imports, but only works with entries that are already there; new files and folders come from a shell.
- **Nothing is off limits in the browser** — it reaches the whole Debian tree, including system files a stray delete would break. Only the tree's own roots (the rootfs, the projects folder, `/tmp`) are protected from rename and delete.
- **Symlinks out of their root** are listed but not followed — a link that resolves outside the rootfs, the projects folder or `/tmp` does nothing when opened or deleted.
- **Sessions cost memory** — each one is a full proot + PTY + shell, so a phone will not hold many at once. They now accumulate across projects until closed or reaped, so the count on the project list is worth reading.
- **proot constraints** — same class of limits as the chat sandbox (no OpenSSH ControlMaster, no real mounts, some modern syscalls may fail).
