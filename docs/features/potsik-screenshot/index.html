    The screen mode — «Экран»

    The third button of the cloud: one frame of whatever is on the screen, then a question about it. The picture and the question go to the current chat as one message, exactly like a photo picked from the gallery.

    The feature only exists where the cloud does (Android 13+, «Поверх окон» — see Потсики). MediaProjection itself is available from API 21, but a screenshot with a question about it needs the overlay to show the answer, so the Android 13 gate of the overlay already covers it and no extra branch was added.

    The flow

    Step What the user sees
    Tap «Экран» No session yet → the system consent dialog; the pill says «Нужно разрешение на снимок экрана» and offers no buttons
    Dialog answered yes One frame is taken; the pill shows a 64×64 dp thumbnail, «Скриншот 1080×2400» and [×]
    Tap the pill The question field of Flow 2, with the placeholder «Спросить про этот экран…» and three chips above it: «Что здесь?» · «Переведи» · «Что не так?»
    Send The picture and the text go to the current chat in one turn; Thinking → WORK_THINKING
    Answer The text in the pill with [Озвучить] and [Открыть в чате]
    Dialog refused errorContainer: «Без разрешения снимок недоступен» + [Повторить]; the cloud stays open

    A chip fills the draft instead of sending at once: the question is the user's, and the field is where it is written.

    The frame is the screen the user was on

    «Экран» is a button on a window that floats over somebody else's screen, so the frame has to be that screen — not ours, and not the app's. Three things keep it that way:

    • The consent activity lives in a task of its own. It is declared with its own taskAffinity and launchMode="singleInstance", and started with FLAG_ACTIVITY_NEW_TASK. Without the affinity, the intent joins the app's task: the system brings that whole task to the front, the transparent activity sits on top of the last Pots screen, and the frame taken after the answer shows the app's settings instead of the desktop the user was looking at. With it, the consent task is the only thing that comes forward and what stays underneath is the screen the user was on.
    • Потсик is not in the picture. Both overlay windows carry FLAG_SECURE, so the system composites them out of the capture (see below).
    • The first frame waits for the screen to settle. The consent activity finishes on the main thread of the same process, and its task leaves the front a frame or two later; PotsikScreenCaptureService asks for the first frame after CONSENT_SETTLE_MS (150 ms) instead of in the same frame the display is created, so the shot is of the screen that is really there. Later taps in the same session are not delayed: nothing is transitioning then.

    If a shot ever does come out wrong on a particular OEM build, the pill still says what it is doing («Нужно разрешение на снимок экрана» while the dialog is up) and offers [Повторить] on failure, so the feature never looks dead.

    Consent is granted once per mode

    The system dialog on every tap is a feature nobody uses, so the session is created once and lives while the cloud is open:

    • the first «Экран» in a cloud raises the dialog; every later tap in the same cloud takes a frame from the session that already lives — no dialog;
    • [×] on the shot pill removes the frame but not the session: the next tap is instant;
    • closing the cloud (a tap outside it, [×], a second double tap, the app coming back, a rotation, the screen going off) ends the mode: the projection is released, the foreground service stops, the notification and the status-bar chip go away.

    The next cloud therefore asks for consent again. That is not an oversight: the MediaProjection token is one-shot. createVirtualDisplay() may be called exactly once per consent, and a second call — or reusing the consent intent — throws SecurityException on Android 14+. The mode keeps the virtual display alive and reads a frame from it on demand; that is why repeated taps are free and a new cloud costs a new consent.

    MediaProjection.Callback is registered before createVirtualDisplay (the platform throws IllegalStateException otherwise) and is what tells the cloud that the projection is gone: the lock screen (Android 15 QPR1+), the status-bar chip, or the system taking it away for its own reasons. That shows as «Доступ к экрану закрыт» + [Повторить], and nothing typed is thrown away.

    Android 14 and 15

    • Android 14+ offers «a single app» in the consent dialog by default, which is the wrong thing to offer for "what is on my screen". The whole display is asked for explicitly with createScreenCaptureIntent(MediaProjectionConfig.createConfigForDefaultDisplay()). The decision is the pure potsikScreenCaptureRequest(sdkInt): on Android 13 and below it returns the plain intent, which is all the platform has, and the screenshot works the same. The version check is inside that function, not around the feature.
    • Android 15 QPR1+ shows a chip in the status bar while the projection lives, and stops the projection when the screen is locked. The chip is the second reason the mode ends with the cloud: a projection with no surface on screen would be a chip nobody asked for.

    FLAG_SECURE: Потсик is not in his own screenshot

    Both overlay windows — the character and the cloud — are created with FLAG_SECURE. Without it the screenshot would show Потсик standing on it and the capsule with the thumbnail of the previous screenshot in it, which reads as a broken feature. The system composites those windows out of the capture.

    The side effect is honest and intended: a screenshot of the desktop pet's own window is impossible for anyone, which is also what keeps the capsule out of screen recordings.

    The frame itself

    The reader is created as RGBA_8888 at the display's own size. The plane the platform hands back is not width * 4 bytes per row — the hardware aligns rows to rowStride, usually wider than the picture. Reading the buffer as one continuous block shears the image diagonally and tints it: the classic "the screenshot is green noise" bug.

    So the copy walks the rows itself (potsikRepackRgba): width pixels of pixelStride bytes each, starting at y * rowStride. It is pure arithmetic on ByteArray, tested on synthetic planes with a tight row stride, a padded one and a wider pixel stride, with no device involved.

    The first frame of a fresh mirror is often not there yet — the display has to draw something first — so the reader is polled for up to a second before the mode gives up and says «Не удалось снять экран».

    The picture is written to the app cache as a PNG and handed to the chat as a PlatformFile, the same type the picker and the camera produce. The chat's own pipeline classifies, compresses and attaches it, so the message in the history is an ordinary message with a picture — no second message format.

    What is not here

    • Downscaling for providers with a small image limit (the spec's «Сжато до 1440»): the chat's pipeline already compresses images, and a second cap would need a measured limit per provider. Its own card if it turns out to matter.
    • The black frame of an app that forbids screenshots (FLAG_SECURE under us — banking, DRM) is not told apart from an empty one: both end in «Не удалось снять экран». Telling them apart needs a heuristic on the pixels, and guessing wrong is worse than the honest message.
